# 팩트너 알림과 복구 운영

운영 상호, 고객 문의 주소, 알림 수신 주소는 미정이다. 정식 접수는 계속 꺼두며, 주소를 추측해서 등록하거나 메일을 보내지 않는다. 이 문서는 2026-10-20 기준이다.

## 새 견적과 오류 확인

- 새 견적과 알림 대기 행을 같은 D1 트랜잭션에 저장한다. 알림 저장에 실패하면 견적 접수도 성공으로 응답하지 않는다. 고객의 같은 접수 번호 재시도는 새 견적을 만들지 않는다.
- 관리자 **견적 관리**가 접수 확인의 기준이다. **알림·운영 상태**에서 대기/실패, 마지막 예약 작업, 마지막 발송 접수와 오류를 확인한다.
- 5분마다 최대 8건을 처리한다. 동시 실행은 원자적 임대 처리로 분리하고, 작업이 중단되면 2분 뒤 다시 가져온다. 실패 간격은 5분부터 늘어나 최대 6시간이며 8회 실패 후 수동 확인을 기다린다.
- 메일에는 접수 번호와 관리자 주소만 포함한다. 고객 이름·이메일·제작 요청·접수 키·내부 메모를 포함하지 않는다. 오류에는 정해진 코드/발생 위치만 보관하고 같은 오류를 1시간 단위로 묶는다. 원문 요청과 비밀번호는 기록하지 않는다.
- 발송 접수는 제공자의 messageId 응답이 있었다는 뜻이다. 실제 받은 편지함 배달 보장은 아니다. 이메일 서비스 응답 직후 DB 기록에 실패하면 같은 알림이 다시 갈 수 있다. 운영 오류 기록은 90일/최대 1,000개, 발송 완료 기록은 90일 정리하며 견적 삭제 시 관련 알림도 지운다.
- Worker/D1 전체 장애 중에는 같은 시스템에 오류를 저장하거나 메일을 발송할 수 없다. Cloudflare 상태 페이지 및 계정 알림도 함께 확인한다. 외부 가용성 알림의 수신자도 확정 후 연결한다.

## 수신 주소가 확정된 뒤

1. 승인된 수신 주소를 Cloudflare 계정의 목적지 주소로 등록하고, 해당 메일함에서 인증한다. 팩트너 도메인의 발신 설정을 완료한다. 무료 인증 목적지 발송 범위에서 준비하고 유료 플랜을 자동 구매하지 않는다.
2. `factner-admin`의 `send_email` 바인딩 이름을 `EMAIL`, `destination_address`를 그 인증 주소 하나로 제한한다. `NOTIFY_TO`에 동일한 소문자 주소, `NOTIFY_FROM`에 인증된 `@factner.com` 발신 주소를 설정한다. 다른 프로젝트의 메일/DNS 설정을 수정하지 않는다.
3. 관리자 **알림·운영 상태**에 동일한 주소를 저장하고 알림을 켠다. 주소만 저장하면 발송되지 않는다. 인증 주소와 바인딩이 맞아야 켤 수 있다.
4. **테스트 알림 예약** 후 다음 5분 작업을 기다린다. 받은 편지함과 Cloudflare 발송 기록을 확인한다. 수신 주소 변경 시 먼저 알림을 끄고 1~4를 반복한다.
5. 쌓인 테스트 견적 알림도 발송 대상이 될 수 있으므로 켜기 전에 테스트 견적을 정리하거나 목록을 검토한다.

사용 API는 Cloudflare 네이티브 `env.EMAIL.send({from,to,subject,text})`이며, 외부 메일 라이브러리·API 키·유료 서비스는 추가하지 않았다. [Workers 이메일 API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/), [발송 바인딩 제한](https://developers.cloudflare.com/email-service/configuration/send-bindings/), [도메인 연결](https://developers.cloudflare.com/email-service/get-started/send-emails/).

## 매일 확인할 것

견적 관리에 신규 접수가 있는지, 알림·운영 상태에 실패가 있는지 확인한다. 마지막 예약 작업이 15분 넘게 갱신되지 않았다면 `factner-admin` Cron 실행 기록을 확인한다. 오류가 반복되면 코드와 발생 시각으로 개발 담당자에게 전달하고 고객 원문을 일반 로그에 붙여넣지 않는다.

## 백업과 안전한 복구 연습

D1 Time Travel은 자동으로 켜져 있다. 복구 가능 기간은 Workers 무료 7일/유료 30일이며, 현 플랜에서 실제 조회되는 시점과 북마크를 확인한다. 별도의 유료 저장소를 만들지 않았다. [D1 복구 안내](https://developers.cloudflare.com/d1/reference/time-travel/), [요금제별 한도](https://developers.cloudflare.com/d1/platform/limits/).

배포 전 또는 복구 점검 시 저장소 루트에서 실행한다. Node.js 24와 이 프로젝트에 설치된 Wrangler 인증이 필요하다.

```sh
node scripts/backup-check.mjs --remote
```

이 명령은 **factner-db**의 현재 북마크와 SQL을 읽어 `.qa/backups/`에 저장한다. 원격 데이터에는 쓰지 않으며, 복구는 별도 임시 로컬 SQLite 파일에서만 연습한다. 무결성·외래키·필수 테이블을 검사하고 행 개수와 SHA-256을 보고서로 남긴 후 임시 복구본은 지운다. 원격 내보내기 동안 데이터베이스 요청이 잠시 대기할 수 있어 접수가 적은 시간에 실행한다. [D1 내보내기 동작](https://developers.cloudflare.com/d1/best-practices/import-export-data/).

기존 SQL만 재검사하려면 다음을 실행한다.

```sh
node scripts/backup-check.mjs --file /절대경로/팩트너-export.sql
```

백업은 고객 정보와 비밀번호 해시를 포함한다. `.qa/`는 Git에서 제외되고 백업 폴더는 소유자만 읽고 쓸 수 있다. 공유 링크나 Git에 올리지 않는다. 시점 복구 외 장기 보관은 현재 구성하지 않았으며, 정식 접수 전에 조직 소유 암호화 저장소와 보관·삭제 책임자를 정한다. 임시 점검 SQL은 확인 후 7일 이내에 삭제하고 결과 보고서만 보관한다.

관리자는 아이디와 비밀번호로 로그인한다. 인증 앱 기능과 배포 비밀값은 제거했다. 과거 백업을 복원할 때도 현재 로그인 방식과 마이그레이션 적용 상태를 확인한다.

2026-10-20 10:27 KST에 인증 앱 제거 마이그레이션 적용 후 운영 DB를 읽기 전용으로 내보내고 별도 로컬 SQLite에 복원해 무결성·외래키 검사를 통과했다. 관리자 1명, 견적 2건, 견적 기록 3건, 알림 대기 1건을 확인했다. 백업 검사 자체는 운영 DB를 수정하지 않았다. 상세 북마크·SQL·결과 보고서는 공유하지 않는 `.qa/backups/`에 있다. 조회한 메타데이터에는 계정의 복구 보존 일수가 표시되지 않았으므로 무료 7일/유료 30일은 공식 요금제 한도이며 계정별 실측 결과가 아니다.

## 실제 장애 시 복구 순서

1. 관리자에서 정식 접수를 끄고 장애 시각(한국시간과 UTC)을 기록한다. 데이터가 손상됐어도 먼저 위 명령으로 현 상태를 별도 보관한다.
2. 수정 전 정상 시점의 북마크를 `npx wrangler d1 time-travel info factner-db --timestamp='<ISO 시각>' --config wrangler.jsonc`로 조회한다.
3. 운영자와 복구 시각·영향 범위를 확정한다. 실제 Time Travel 복구는 현재 데이터를 덮어쓰고 진행 중 쿼리를 취소하므로 자동 실행하지 않는다. 명령 형태는 `npx wrangler d1 time-travel restore factner-db --bookmark='<확정 북마크>' --config wrangler.jsonc`이다.
4. 복구 직후 북마크를 보관하고 관리자 로그인, 견적 목록, 고객 조회, 업체 정보, 알림 설정을 확인한다. 복구 사이에 접수된 견적은 1단계 SQL과 비교해 필요한 행만 복원한다.
5. 복구로 이전 세션이나 처리 완료 알림이 되살아날 수 있다. 모든 관리자 세션을 해제하고 알림 발송 이력을 대조한 뒤 접수와 알림을 재개한다. 당시 코드와 복구된 DB 스키마가 맞는지도 확인한다.

이 절차는 운영 DB에 실제 복구 명령을 실행했다는 뜻이 아니다. 평상시 점검은 읽기 전용 내보내기와 로컬 복구 연습까지만 수행한다.
