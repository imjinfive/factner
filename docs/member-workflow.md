# 회원·업체 관리와 검토 흐름

2026-10-27 사용자 요청 반영. 이전 익명 예시 후보·자유 사양 발주 흐름보다 우선한다.

## 운영 순서

1. 회원 가입 신청을 심사해 승인한다. 가입 대기 회원은 로그인할 수 없다.
2. **회원·업체 관리 → 회원 이름 → 업체 상세 입력**에서 소개, 품목, 수량, 생산 희망 기간, 납품 조건 등을 입력한다. 확인된 내용만 입력하고 후보 표시를 켠다. 연락처·상호·내부 기록은 후보 응답에 포함하지 않는다.
3. 브랜드의 패키징 사진·사양은 같은 회원 상세의 **패키징·사진 관리**에서 등록한다. 브랜드가 직접 추가·수정한 경우 검토 대기 요청이 생성된다. 승인 전에는 기존 사양을 덮어쓰지 않는다.
4. 로그인한 브랜드는 제작 업체를, 제작 업체는 브랜드를 품목별로 검색하고 여러 후보를 선택한다. 지역은 무관이며 예시 데이터로 빈 결과를 채우지 않는다.
5. 관리자 **파트너 선택 요청**에서 요청자와 대상자를 확인한다. 실제 거래 조건을 양측과 확인한 뒤 **거래 연결**한다. 처리 완료라는 기록만으로 거래를 생성하지 않는다.
6. 새 발주는 활성 거래 관계와 승인된 자기 계정의 패키징이 있어야 한다. 요청 시 승인 사양 버전을 확인하고 스냅샷으로 보관한다. 수량·납기·배송지와 자료 전달 동의를 다시 확인한다.

## 기존 자료

- 회원·기존 발주·파일을 삭제하지 않는다. `0011_member_workflow.sql`은 업체 프로필, 선택 요청, 사양 검토 기록과 발주 사양 참조를 추가한다.
- 기존 패키징은 자동으로 검증된 것으로 간주하지 않고 검토 대기로 옮긴다. 기존 발주 스냅샷은 바꾸지 않는다.
- 회원 계정과 무관한 예전 업체 자료는 회원·업체 관리 하단의 별도 보관 링크로 접근한다.
- 거래 연결 전에는 마이페이지의 발주 탭과 새 발주 기능을 노출하지 않는다. 예전 발주가 있으면 내 정보의 이전 발주 기록에서 열람할 수 있다.

## 확인 화면과 알림

주요 제출·수정은 입력 내용을 표시하는 확인 창을 거친다. 비밀번호와 복구 코드는 확인 요약에 표시하지 않는다. 계정 복구는 기존 본인 확인·단일 사용 코드 방식을 유지한다.

관리자 상단과 메뉴에 비밀번호 복구·후보 선택·사양 검토 대기 건수가 표시된다. 20초마다 갱신하며 실패 시 마지막 건수와 갱신 오류를 표시한다. 문서·이메일 알림 발송과는 별개이며 외부 메시지는 자동으로 보내지 않는다.

대표 관리자 로그인 첫 화면은 회원·업체 관리이며, 일반 관리자는 발주 관리로 진입한다.

## 검증

`npm test`, `npm --prefix rebate-ui run build -- --configLoader native`, 관리자 JavaScript 구문 검사를 실행한다. 로컬 실제 Worker·SQLite에서 회원 간 접근 차단, 복수 선택, 미승인 사양/미연결 발주 차단, 승인 충돌과 기존 자료 보존을 검사한다. 운영 배포 전 백업 및 복구 무결성 검사 후 마이그레이션을 적용한다.

2026-10-27 배포 검증: 자동 검사 88개 통과, 고객 화면 빌드·관리자 구문 검사 통과. Chrome에서 가입·후보 선택 뒤로/앞으로 이동, 양방향 복수 선택, 패키징 검토 및 기존 사양 유지, 주문 접수와 견적 확인 창을 로컬에서 검증했다. 운영에서는 회원 3개, 패키징 1개, 발주 1개, 복구 요청 1개가 보존되었으며 기존 패키징 검토 대기 1개와 외래키 무결성을 확인했다. 실제 거래 연결·주문·복구 코드 발급은 운영 검증 중 수행하지 않았다.
